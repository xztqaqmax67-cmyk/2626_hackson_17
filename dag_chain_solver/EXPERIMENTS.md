# 鏈剖分 v0.1 實驗紀錄

日期：2026-10-30。這是本機實驗，並非主辦方正式成績。

## 驗證方法

- 使用本庫原始 `hackathon_data/case_00.json` 至 `case_09.json`，每例測 2、3、4、5 核。
- 固定 L1=1572864、UB=131072、DDR=60、跨核等待=1000。
- 外部評估器為既有 `前辈代码_cpp` 場景 B 移植版的 `parity_runner`；求解器執行期不依賴它。
- 每組同時測鏈版和同模型的逐算子消融基線，共 80 次完整評估；每個方案另重跑一次並比對位元組。
- 抽查 case_01、case_07 的四核鏈方案，用原 Python 場景 B 程式重評，Makespan 及搬運量全部相同。
  只在記憶體中增加 PIPE_FIX、將 COPY 的 -1 佔位改為 1，原始檔案不變。
- 另生成 20 個小型隨機 DAG，涵蓋全部五條 Pipe、分叉、匯合、多寫入 Tensor、打亂輸入順序，
  各測 2、5 核，共 40 組外部評估與重複輸出檢查，全數通過。

## 公開資料結果

鏈版 **40/40** 通過外部評估；基線 **40/40** 通過。所有重跑輸出完全一致。

相對於移除鏈搜尋的消融基線：**20 組更快、18 組相同、2 組更慢**。
每組 Makespan 降幅 `1 - T_chain / T_baseline` 的算術平均為 **12.3403%**。
這個數字不是官方加速比：官方單核基準未提供，且這兩個方法並非等求解時間比較。

首輪 MSVC 測量：四核 10 例求解時間合計 **8.293 秒**；全部 40 組中單次最長 **2.114 秒**。
這些時間包含程式啟動、輸入讀取與方案寫出，不含編譯、外部評估和重跑驗證。
同機同時可能存在其他工作，不能當作標準化硬體基準。

完整資料：`runs/all_cores/report.json`，包括原始輸入 SHA-256、每例搬運量、求解和評估耗時。
原 Python 抽查：`runs/python_reference.json`。隨機圖：`runs/random_check/report.json`。

另以 MSVC／MinGW 各自重建，兩者生成的 40 份方案均與上述已評估方案逐位元組相同。
比對紀錄為 `runs/msvc_final_match/comparison.json`、`runs/mingw_match/comparison.json`。
MSVC 重跑期間讀取 Windows 的程序峰值工作集，最大觀測值 **87,506,944 bytes（約 83.5 MiB）**。
此欄位為工作集觀測，並非跨平台的記憶體使用上限證明。命令列測試另覆蓋中文／空格路徑、
預設輸出位置、兩種參數格式、拒絕配置覆寫、退出碼及失敗時保留既有方案。

## 已發現的限制

1. 初版 case_07 的鏈方案在完整模擬中死鎖。診斷顯示某核心換出了尚有後續寫入的 Tensor。
   已加入「多次寫入之間換出」候選排除，並新增針對這個機制的單元測試；修正後全部公開配置通過。
2. 內部估價仍可能誤選：case_05 三核、case_06 四核比逐算子基線慢。
   現有估價沒有完整重現共享 DDR、FIFO 與非同步記憶體重用，所以擴大候選池不保證外部成績單調改善。
3. 多寫入者同核是保守限制；它可能減少可探索的分配方式。
4. 各核數分別求解，沒有保證增加核心後的 Makespan 單調下降。
5. 比較對象是本實驗的逐算子消融基線，不是 `前辈代码_cpp` 的完整多路線搜尋。
   尚未做與該版本的等預算對照，也沒有用測試用例名稱或預生成方案作特判。
6. Windows MSVC 19.44 與 MinGW GCC 15.1 已實際編譯、執行。Linux GCC 9.4/11 的構建與執行仍需在 Linux 環境驗證。

下一步建議：針對內部估價與外部結果排序不一致的候選，改善 DDR 競爭及溢出預測；
之後再做相同求解時間下的原多路線搜尋／鏈初解搜尋比較。
