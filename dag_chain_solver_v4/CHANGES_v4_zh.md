# v4 修改與接手摘要

本目錄是從 `dag_chain_solver_v3` 的 0.3.1 獨立建立的 0.4.0。
v3 程式、原評分器、原始資料與 `hackathon.zip` 均未修改。
v3 原始碼 SHA-256 記錄在 `reports/v3_source_manifest.json`。

## 實作內容

| 方向 | v4 實作 |
|---|---|
| DAG 完成時間 | 完成時間一律使用所有前驅的最大值；通訊權重只影響偏好父節點，不能讓匯合點漏等較長分支。 |
| 路徑覆蓋 | 首選前驅已被別的後繼占用時，嘗試其他空閒前驅。這是貪婪極大覆蓋，沒有宣稱求得最少鏈數。 |
| 分段與記憶體 | 保留按 Pipe 負載切段，增加按 Tensor 足跡切段的候選；同一 Tensor 的寫入者仍為不可拆開的放置單位。 |
| 候選多樣性 | 粗篩兼顧估計時間、總搬運量、計算排程時間和舊成本模型。保留最多 24 個不同取向候選，另保留舊搜尋軌跡的入圍方案。 |
| 局部搜尋 | 增加 Tensor 相關使用者合併、寫入者群組搬移、兩段交換，以及固定核心分配後的記憶體導向重排。 |
| 粗估價 | 移除 DDR 已成瓶頸時再將整份 spill 時間疊加一次的計算。粗估只用於篩選，最終比較採事件估價。 |
| 細化估價 | 自寫邊界 COPY／spill COPY 事件、固定 Pipe FIFO、跨核等待與容量重用依賴；DDR 操作啟動／完成時重新分配共享帶寬。 |
| 核心數選擇 | 2 到 N 核的候選使用同一套細化 cycles／搬運量排序，移除舊版只對較少核心方案使用的保守門檻。 |
| 共用分析 | 最長路徑、邊搬運量和 4 種路徑覆蓋在各核心數搜尋之間共用，保持固定工作量及確定性。 |

`src/chain.cpp` 負責路徑、分段、候選搜尋與選擇；`src/refine.cpp` 負責細化估價；
`src/model.hpp` 保留圖解析、放置草圖、搬運量帳本與粗記憶體估算。

## 規則與可重現性

以新版 config 為準：L1 1,572,864 bytes，UB 131,072 bytes，DDR 60 bytes/cycle，
COPY_OUT 完成後等 1,000 cycles 才可開始跨核 COPY_IN。不要改回舊文件的容量或同步值。
90% 為溢出處理的軟門檻，不是硬容量；當前操作的必要輸入／輸出不可作為 victim。
新版原評分器支援部分寫入 Tensor 換出，v4 不將它一律當成非法方案。

正式生成器不讀取測試答案、不呼叫 Python、原評分器或外部程序。
研究工具在 `scripts/` 與 `tests/`，原評分器副本在被 git 忽略的 `references/`；
`scripts/package.py` 只打包 CMake、README、src。

測試的基準是同一份新附件內的 `singlecore_evaluate.py`。沿用 v3 已完成的 10 個單核結果，
並核對資料、config、所有評分器源碼及結果的雜湊。副本在 `reports/singlecore_baseline/`，
v3 比較結果在 `reports/v3_baseline_20261030.json`。不能把舊題目包的單核 cycles 混入此表。

## 本次測試

- 10 個用例 × 2～5 核：40/40 通過未修改的新版原評分器。
- 每組生成兩次：40/40 位元組一致，並通過同 Tensor 寫入者同核與原 DAG 拓撲檢查。
- 40 組加速比算術平均：v3 **1.775120×** → v4 **1.909483×**，提升 **7.57%**。
- 40 組總搬運量合計：7,868,797,248 → 7,235,510,848 bytes，下降 **8.05%**。
- 33 組 cycles 降低、6 組持平；`case_05` 四核由 9,519,460 變為 9,525,184，慢 **0.060%**。
- 最大生成耗時 **6.68 秒**，最大觀測 working set **176.63 MiB**，最大取樣程序執行緒 **7**。
- MSVC 19.44、GCC/MinGW 15.1 都編譯成功，5 組 C++ 測試與 CLI／26 項輸入契約測試通過。

結果與逐組雜湊：`reports/official_v4_20261030.json`。
閱讀表格：`reports/RESULTS_zh.md`；資料表：`reports/official_v4_20261030.csv`。
所有實測 cycles、搬運量均取原評分器輸出，未以內部估價代替。

## 尚有的限制與後續切入點

細化估價不等於原評分器。這 40 組的 cycles 平均絕對誤差為 **0.724%**，最大 **3.568%**；
29 組總搬運 bytes 完全一致。誤差明細在 `reports/estimate_fidelity.json`。
目前子圖內 COPY 排序及容量重用依賴採自寫模型，與原評分器仍可能不同；
很接近的候選會發生名次交換，`case_05` 四核的微小退步就是值得繼續檢查的情況。
不要聲稱增加可用核心數必然令原評分器實測 cycles 下降。

後續優先比較 `case_05`、`case_08` 的原始 trace 與內部事件，修正名次判斷偏差，再增加
高 spill Tensor 的專項生命週期重排。每次改動重新生成方案，使用新的 runs 子目錄，
保留原評分器／config 雜湊與相同單核基準。

本次在 Windows 測試，未在原生 Linux、指定的 GCC 9.4／11 或 ThreadSanitizer 環境執行。
上述時間與記憶體是本機已提供資料的觀測值，不是未知資料的最壞情況保證。
