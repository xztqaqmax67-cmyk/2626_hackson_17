# DAG Chain Solver v9（0.9.0）

v9 將「搬運成本主導的同核分組」與「依完整 DAG 決定執行順序」分開。新版本位於獨立目錄，v8 0.8.1 的源碼、執行檔、報告與原始結果保留不動。

## 核心想法

鏈是分核約束：同一個最後形成的鏈段／群組必須放在同一核心，但群組內運算不需要連續執行。其他群組的運算可以穿插；排程器仍逐一檢查原始 DAG 的全部依賴，不把群組縮成不可穿插的整塊任務。

連鏈優先保留估計跨核搬運成本大的邊；切鏈優先保留高成本邊、切掉較低成本邊。計算時間用於限制群組工作量、分核負載平衡及最終估時，不再作為新版連鏈的首要排序依據。

## 執行流程

1. 執行完整 v8 搜尋與溢出回饋，取得保底方案。正式程式自行計算，不讀歷史結果或其他版本執行檔。
2. 對 2～可用核心上限，產生搬運主導的路徑覆蓋，以一致的搬運成本優先規則處理連鏈與多後繼競爭。
3. 將路徑切成有界鏈段，在每條鏈上尋找成本較低的切邊，所有候選限制節點數與各 Pipe 工作量；保守候選另限制 Tensor footprint，另一候選允許聯集較大的群組，交由完整預演判斷實際溢出。必要的同 Tensor writer 群組會合併；搜尋限制不構成額外輸入合法性要求。
4. 分核仍考慮各 Pipe 負載及以 Tensor 核心集合計算的邊界搬運。每種分組分別嘗試 critical／DFS 就緒優先序；不強制鏈段相鄰運算連續執行。
5. 全部核心預算共用有界細化額度，重新評估 cycles 與官方 Step2 精確總搬運量；最多對一個新分組方案追加 v8 的有界溢出回饋。中間候選可暫時比入口搬運更多，以保留調整排序的機會；最終接受條件不放寬。
6. 新版候選帶有內部 `placement_group`，後續移核必須連同整個群組及 writer 閉包一起移動。正式輸出 JSON 不包含這個內部欄位。
7. 最終只接受估計 cycles 與精確總 COPY 均不高於入口 v8 方案、且至少一項嚴格改善的結果；否則輸出入口方案。選優以 cycles 為先，總搬運量次之。

## 成本與限制

連鏈是貪心路徑覆蓋，不宣稱全域最大權或最少鏈數；DP只在已選路徑、回看窗口和各候選啟用的搜尋限制內找低成本切點。writer群組合併後還會重新檢查限制，可能增加切邊。Tensor footprint是群組碰到的Tensor大小聯集，不是實際同時駐留峰值，直接op-op邊的合成緩衝會在完整trace中另行計入。

連鏈使用的邊搬運權重是啟發式。多個消費者在同一目的核心會共用一次跨核 Tensor 搬運，因此邊權和不等於真正可節省字節數；最終以完整分配的邊界搬運與 Step2 重播校驗。較少搬運也不保證更短官方時間，因為仍有負載、Pipe、同步與溢出的交互影響。

C++ 精確移植範圍仍是本求解器單節點子圖表示的官方 Scene B 圖構造、Step1、Step2。**完整官方 Step3 尚未移植，內部 cycles 仍使用 `refine.cpp` 近似模型。** 所有正式比較表另由未修改的官方評分器測得，保留任何改善、持平與退步。

本版不修改硬體容量、90% 軟閾值、DDR 帶寬或 1000 cycles 跨核延遲，不刪除原始 DAG 邊，不使用用例名稱、答案表或資料特判。預設固定搜尋數量且可重現；不同輸入的 CPU 生成時間不固定。

## 建置與執行

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release --parallel 4
build/bin/npu_sched input.json -n 5 -o output/plan.json
```

Windows 使用 `.exe`。核心數上限 2～5，預設 4；允許空核。正式 CLI 及輸出格式維持原樣，`--version` 顯示 `dag-chain-solver 0.9.0`。

stderr 的 `feedback_stats {JSON}` 描述前段 v8 回饋，`communication_stats {JSON}` 描述新增分組階段；stdout 不輸出評分。搜尋參數見 [SEARCH_LIMITS_zh.md](SEARCH_LIMITS_zh.md)。

## 開發測試與比較

```sh
cmake -S . -B build -DCHAIN_BUILD_TESTS=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release --parallel 4
ctest --test-dir build -C Release --output-on-failure
python scripts/run_v9_official.py --solver build/bin/npu_sched
python scripts/summarize_v9.py
```

完整目錄含測試與評估工具；精簡源碼 ZIP 只含 src、CMake 與說明，使用預設 `CHAIN_BUILD_TESTS=OFF`。官方原始檔案在 `references/`，不得修改規則。新版40組結果存放於 `runs/official_all/`，比較來源為同層 v8 的 `runs/official_upgrade/`，單核基準仍為相同的官方單核結果。

`spill_diagnostics` 的只讀模式可重播輸出方案；它的 `--improve` 模式不能從正式方案 JSON 還原內部群組，所以不代表正式 v9 保留群組的後處理。實驗時請用新的輸出目錄，避免混合來源雜湊。

唯一採用新分組的是 case_09 五核：官方 cycles **3,778,277 → 3,671,975（−2.81%）**，總 COPY **165,968,320 → 148,927,104 bytes（−10.27%）**，但溢出 **73,153,792 → 78,095,424 bytes（+6.76%）**。搬運量的淨減少來自邊界搬運減少足以抵銷額外溢出，不能把它描述成溢出優化成功；cycles 的變化未做單一因素因果實驗。

本輪平均方案生成時間為 **6.210 秒**，v8 先前記錄為 **5.336 秒**，約增加 16.38%；兩者分開量測，時間不含官方評分。這版驗證了新想法可帶來個別收益，但目前整體收益很小，且有額外搜尋成本。其餘 39 組輸出與 v8 逐字節相同，保底方案由 v9 自行計算。

MSVC 19.44 與 MinGW/GCC 15.1 均通過 13/13 項 CTest；CLI、26 項圖輸入約束檢查、64 組合成圖官方評分及重複生成一致性檢查也通過。另以最終版本完成 120/120 組 Step1／Step2 差分核對（40 組正式方案、64 組合成圖、16 組邊界案例），搬運分類、溢出記錄與核內序列均符合官方對照。已核對 v8 保存清單的 96 個檔案未改動。原生 Linux 與舊版 GCC 未在本電腦測試。
