# 官方评测器对齐记录（2026-10-30）

已将用户提供的 `hackathon.zip` 中代码、数据、配置和说明原样保存到 `official_evaluator/`，不导入压缩包的 `.git`。`SOURCE_MANIFEST.json` 记录压缩包和 24 个原文件的 SHA-256；测试启动时校验原件。

当前场景 B 的搜索完整评分已对齐此版本。正式入口 `npu_sched` 和开发入口 `problem2` 共用修正后的 C++ 评估函数；外部复评和链初解基准默认调用未修改的官方 Python。搜索中的草图/代理估价仍用于候选预筛，不应当作最终成绩。

## 已修正的差异

| 项目 | 修正前内部实现 | 当前官方口径与修正 |
|---|---|---|
| Step2 换出触发 | 超过硬容量才换出 | 超过硬容量的 90% 提前换出，取整数下界；当前指令无法再换出时，只要不超过硬容量仍可执行 |
| 多写者换出 | 只重接消费者边 | 后续写者与消费者均连接到换入的新版本 |
| DDR backing | 已有备份就复用 | 上次同步后发生写入则重新 COPY_OUT，干净备份仍复用 |
| 扩展序列检查 | 未检查 Step2 输出的全部拓扑关系 | 校验直接算子依赖和经过张量的依赖 |
| 方案合法性和随机示例 | 独立评分入口未拒绝跨核多写者，随机示例可能拆散写者 | 拒绝同一张量写者跨核；随机生成器按共享写者子图分组分核 |
| Python 对照来源 | 旧数模评测器加 PIPE_FIX 补丁，改写 COPY 占位值 | 直接加载此次官方原件，保留原始输入 |

`PIPE_FIX`、`COPY cycles=-1`、L1=1,572,864、UB=131,072、DDR=60 和跨核等待=1000 在 C++ 中此前已对齐，无需再更改。官方的跨核事件模拟主体与旧 Python 同名文件一致；本轮差异主要来自 Step2 和方案校验。

## 验证与使用

- Windows / MinGW GCC 16.1、C++17 编译成功；8/8 组 CTest 通过。
- 新语义测试覆盖 90% 边界、软阈值瞬态、硬容量拒绝、干净备份复用、脏回写、多写者重命名、扩展序列拓扑和 2/3/4/5 核的完整评分。
- 两批真实数据复评共 20/20 完整结果一致；链初解基准的默认官方 Python 路径已实跑验证。默认 build/bin 工具已更新；正式 npu_sched 示例输出再次通过官方复评（74 cycles）。
- 修改评分源码会改变编译时评分器指纹；新的基准缓存键包含官方原件和适配层哈希，旧缓存不会自动当作新官方评分复用。
- 旧链初解报告中的分数属于旧口径；本报告提供同方案的新口径。没有重跑所有候选的排名，也没有重跑整批 90 秒优化。

在 `前辈代码_cpp` 目录执行（需要先构建测试目标 `parity_runner`）：

```powershell
python tests/compare_official_scores.py --plans output/hackathon_cores_4 --out output/official_recheck
```

脚本默认读取 `official_evaluator/data/` 和其官方配置，保存逐例差异、耗时、来源哈希和汇总 CSV；任何官方失败或新内部结果差异都会返回非零。可用 `--inputs` 指向其他图目录，`--runner` 指向指定构建的 `parity_runner`。

直接运行原版官方命令：

```powershell
python official_evaluator/code/multicore_cut_evaluate_problem_2.py official_evaluator/data/case_00.json output/hackathon_cores_4/case_00_multicore_res.json --config official_evaluator/data/config.txt -o output/official_case_00.json
```

官方包中的问题 1、3、单核模块作为原包参考依赖保留；本次 C++ 对齐和实测范围是当前工程维护的场景 B。
