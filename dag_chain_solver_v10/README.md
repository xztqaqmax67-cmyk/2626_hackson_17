# DAG Chain Solver v10（0.10.1）

v10 在每次重新執行完整 v9 搜尋後，增加 Tensor 共用分組、溢出熱點調整、多起點回饋，以及最後候選的官方計時移植。0.10.1 保留 0.10.0 的 3 個精算候選，再擴充至 6 個，並增加依精確時間線與溢出記錄提出的單輪調序。正式輸出格式仍只有 node_to_subgraph 與 core_schedules。v9 保存在同層原目錄；所有保底方案都在本次重新求解，不讀歷史答案作為求解輸入。

## 算法流程

1. 完整執行 v9，取得本次算出的入口方案。
2. 按 Tensor 的來源／目的核心集合評估實際邊際搬運；嘗試生產者與多個消費者同核、共用輸入消費者聚合，以及從溢出／負載熱點拆出 writer 完整的小組。群組只約束分核，完整 DAG 仍決定就緒與順序。
3. 用 Pipe 負載及資料存活區間壓力篩選候選，並加入由實際溢出記錄提出的純排序候選。Tensor 大小聯集不等於同時駐留量，搜尋啟發式不能成為額外合法性限制。
4. 最多 8 個候選進入精確 Step2 搬運重播及原有近似細估。保留低時間、低溢出、低邊界搬運的不同起點；最多 3 個起點共用 48 次重播／12 次細估，而非每個起點各用一份預算。
5. 按原選法建立最多 3 個精算候選，包含本次 v9 入口；原候選與平手順序完整保留，再由既有候選池補至最多 6 個。精確模型包括官方逐核 Step3 的 Pipe 排布、容量重用依賴及後續 Scene B 全域事件模擬，保留這 6 個方案中的最佳者。
6. 以第 5 步的最佳方案為同一個固定起點，最多產生 4 個時間線調序與 4 個溢出調序候選。時間線用 Pipe 空檔和延遲下游工作的情況安排優先序，移動完整前驅閉包；不修改分核或同核群組約束。兩種候選交替精算、按正式核心序列去重，只做一輪，不把接受的新方案繼續展開。全程最多 **14 次完整多核方案精算**，不是每核各 14 次。

精確選優先比較 cycles，cycles 相同才比較總搬運，保留舊 3 個候選及擴充池的最佳結果。cycles 較低時可接受較多搬運；所有 DAG、writer、容量和執行依賴約束仍須滿足。前段近似模型或搬運量單項不再否決這一輪已由精確計時確認的改進。尾段勝出後重算近似估價僅更新診斷，不改寫精確選優結果。

Step 2 後的實體版本查找亦改用二分：若某 Tensor 有 S 次溢出，每條使用邊由 O(S) 前綴掃描改為 O(log S) 查找。選中的版本仍是「該操作使用位置之前或當時的最後一次重載」，包含後續寫入者；未更改溢出規則、搬運量或計時模型。

原有 refine.cpp 仍用於前段搜尋，精確模型只作用於最後候選。每組入口及入選方案的精確 cycles 還會與未修改的官方評分器交叉核對；正式表格使用官方評分，並保留全部變體的改善、持平及退步。

移植範圍是本求解器使用的單 Op 子圖 Scene B 表示及固定硬體常數，不是任意子圖格式的通用評分器。ID、字節量和時間使用有檢查的 64 位整數；超出支持範圍會回報無效，最後精算若入口失敗則保留本次 v9 方案，並記錄錯誤。官方 Step3 的整數 set 迭代會影響容量額度的復用順序，因此實作對齊本次官方環境的 **64 位 CPython 3.11.11**，包含雜湊碰撞及大 ID 的行為。換評分器版本或 Python 實作後應重新執行差分核對。

## 建置與使用

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release --parallel 4
build/bin/npu_sched input.json -n 5 -o output/plan.json
```

Windows 的執行檔帶 .exe。正式 CLI 不增加調參旗標；--version 為 dag-chain-solver 0.10.1。搜尋配額見 [SEARCH_LIMITS_zh.md](SEARCH_LIMITS_zh.md) 和 src/search_limits.hpp；時間線閉包與距離的細項預設在 src/timing_feedback.hpp 的 TimingFeedbackLimits。

stderr 分別輸出 feedback_stats、communication_stats、v10_stats JSON。最後一項記錄候選／回饋／精算的本機經過時間、精確呼叫數、入口與輸出 cycles，以及每個精算候選的結果。tail_seconds 已包含在 exact_seconds 中，兩者不可再相加。這些秒數與模擬硬體 cycles 不同；預設是固定工作量，沒有每點 15 秒硬截止。

新版精簡源碼包路徑為 dist/dag_chain_solver_v10_1.zip，只含 src、CMake 及說明；測試、備份工具和官方材料在完整工作目錄中，精簡包使用預設 CHAIN_BUILD_TESTS=OFF。舊版 dist 與原 reports、runs 保留；0.10.0 證據及執行檔雜湊見 reports/upgrade/v10_0_baseline_manifest.json。

## 分階段比較

開發建置設 CHAIN_BUILD_TESTS=ON，另外生成 npu_sched_experiment，可使用：

```sh
build/bin/npu_sched_experiment input.json -n 5 -o plan.json --ablation tensor_memory
build/bin/npu_sched_experiment input.json -n 5 -o plan.json --ablation multi_feedback
build/bin/npu_sched_experiment input.json -n 5 -o plan.json --ablation exact_legacy
build/bin/npu_sched_experiment input.json -n 5 -o plan.json --ablation exact_pool
build/bin/npu_sched_experiment input.json -n 5 -o plan.json --ablation exact
```

另有 v9 模式，用於核對前段仍重新算出相同方案。各變體獨立生成、獨立官方評分，輸出至不同測試目錄；不把某一變體時間當作另一變體的實測時間。

前兩階段沿用近似 cycles 和精確總搬運均不高於入口的保守選優。exact_legacy 重現 0.10.0 的最多 3 個精算候選；exact_pool 保留此前綴並擴充至最多 6 個；exact 再加最多 8 個固定起點尾段候選。精確階段同時引入精確最後選優和允許搬運取捨，因此它與前兩階段的差異不能解讀成純粹更換計時模型的單因素結果。

0.10.1 的比較腳本為 scripts/run_v10_upgrade.py 與 scripts/summarize_v10_upgrade.py。新方案與官方評分分別寫至 runs/upgrade/official_exact_pool、runs/upgrade/official_exact；exact_legacy 相容性抽查寫至 runs/upgrade/official_exact_legacy。新比較報告寫至 reports/upgrade，保留 0.10.0 證據不覆寫。

## 單檔備份

v10 的初始工作副本只複製源碼、測試／腳本、官方材料及必要基準，沒有複製 v9 的 build、runs、dist 或 snapshots。之後每輪修改前使用：

```sh
python scripts/backup_changed.py descriptive_label src/file_a.cpp src/file_b.hpp
```

工具只接受明確的檔案路徑，不接受目錄。備份存於 backups/時間_標籤/，manifest.json 記錄原雜湊；新檔記錄 existed=false。不要整份複製工作目錄作為每輪備份。

## 0.10.0 歷史驗證

- 三個累積版本：各 40 組官方評分，共 120／120 成功。
- 最終版本：120／120 組 C++／官方完整計時差分，包括全部 40 個最終正式方案、64 組合成圖及 16 組邊界案例；比較 cycles、搬運、完整逐操作時間線、Pipe 順序、記憶體峰值和重用依賴 metadata。
- 預檢另涵蓋大 ID／雜湊碰撞與大於 2^53 的時間。104 組預檢包含上述 80 組小圖以及 24 組額外案例；其中 16 個案例由官方及 C++ 一致拒絕，不能算作成功生成的合法方案。
- 獨立固定 seed 的 240 個通用隨機 DAG：135 個官方有效方案全部逐項一致，105 個官方拒絕方案也一致拒絕。
- MSVC 19.44 與 MinGW/GCC 15.1 各 16／16 CTest；CLI、26 項輸入契約、64 組合成圖官方評分及重複輸出一致性通過。

這些結果是測試證據，不是對所有任意輸入的形式化證明。已測平台為 Windows x64，未測原生 Linux 或較舊 GCC。精確計時的數值範圍及官方 Python 順序相依性見前文。
